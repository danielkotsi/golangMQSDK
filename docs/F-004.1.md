# F-004.1: Pre-queued messages silently fall back to shared Incoming — per-consumer entry registered too late

Status: **OPEN** — SDK bug; broker is correct. Blocks the F-004 fix from being
reliable under the pre-queued-delivery scenario.

## Finding

The F-004 SDK v0.3.1 fix creates the per-consumer delivery entry only after
receiving `basic.consume-ok` from the broker (`route`, `BasicConsumeOKType`
case). But the broker's `dispatchLoop` is a separate goroutine: it wakes as
soon as `registerConsumer` is called (`broker/queue.go:47`, `q.cond.Signal()`)
and can write `basic.deliver` envelopes **before** the connection serving
goroutine has written `basic.consume-ok`.

When `basic.deliver` arrives at the client **before** `basic.consume-ok`, the
per-consumer entry does not yet exist in `ch.consumers`, so the delivery falls
through to the legacy shared `ch.Incoming` — nobody reads it. The consumer,
returned by `Consume`, reads exclusively from the per-consumer channel, which
remains empty forever.

## Observed behaviour

`TestMultiProducer_NoConsumerThenAttach` publishes 45 messages to a queue
**before** any consumer is registered, then attaches a consumer via `Consume`.
The consumer expects all 45 deliveries.

Intermittently (observed 1-in-~30 under `-race -count=10`): zero deliveries
arrive on the per-consumer channel within the 5 s timeout:

```
--- FAIL: TestMultiProducer_NoConsumerThenAttach (5.02s)
    multiproducer_test.go:93: timed out after 5s waiting for 1 deliveries; got 0
```

The failure is intermittent because the race depends on goroutine scheduling:
the dispatchLoop must wake and write `basic.deliver` before the connection
serving goroutine writes `basic.consume-ok`. Under the race detector, this
window widens.

The same test runs **20/20 clean** on the base `integrationTests` branch
(before F-004 SDK bump), confirming the flake is introduced by the F-004 SDK
change.

## Why that behaviour

### Broker side (correct)

`HandleConsume` (`broker/channel.go:58-79`):

```go
func (ch *Channel) HandleConsume(env protocol.Envelope) {
    ...
    tag, err := ch.broker.RegisterConsumer(event.ConsumerTag, event.Queue, ch)
    ...
    ch.conn.WriteEnvelope(env.ChannelID, protocol.BasicConsumeOKType, ...)
}
```

`RegisterConsumer` (`broker/broker.go:80`):

```go
func (b *Broker) RegisterConsumer(consumetTag, queue string, ch *Channel) (string, error) {
    ...
    q.registerConsumer(c)          // wakes dispatchLoop
    ch.consumers[c.tag] = c
    return c.tag, nil
}
```

`registerConsumer` (`broker/queue.go:43-48`):

```go
func (q *Queue) registerConsumer(c *Consumer) {
    q.mu.Lock()
    q.consumers[c.tag] = c
    q.mu.Unlock()
    q.cond.Signal()                // dispatchLoop wakes immediately
}
```

Sequence on the broker side (two goroutines, not serialised):

| Connection goroutine (`HandleConsume`) | `dispatchLoop` goroutine |
|----------------------------------------|--------------------------|
| `q.registerConsumer(c)` → `q.cond.Signal()` | *sleeping* |
| `ch.conn.WriteEnvelope(... consume-ok ...)` | *wakes*, picks up consumer |
| | `WriteEnvelope(... basic.deliver ...)` |

The two `WriteEnvelope` calls go through the connection writer. They are
serialised at the write level, but their **temporal order is not guaranteed**:
if `dispatchLoop` wakes and calls `WriteEnvelope` before the connection
goroutine reaches its own `WriteEnvelope`, the `basic.deliver` is written
first. The broker is behaving correctly — it dispatches as soon as the consumer
is registered, which is the right thing for latency and throughput.

### SDK side (the bug)

`route` (`gomqSDK/channels.go:130-148`):

```go
case protocol.BasicDeliverType:
    var delivery protocol.Deliver
    json.Unmarshal(env.Payload, &delivery)

    if delivery.ConsumerTag != "" {
        ch.mu.Lock()
        target := ch.consumers[delivery.ConsumerTag]   // nil — entry not created yet
        ch.mu.Unlock()
        if target != nil {
            target.deliveries <- delivery
            return nil
        }
        // Unknown tag: fall through to the legacy shared sink.
    }
    ch.Incoming <- delivery    // ← delivery lands here, nobody reads it
    return nil
```

`route` (`gomqSDK/channels.go:149-169`):

```go
case protocol.BasicConsumeOKType:
    var consumeOK protocol.ConsumeOK
    json.Unmarshal(env.Payload, &consumeOK)

    // Register the per-consumer channel here, on the readLoop goroutine,
    // before resolving the pending consume. readLoop processes envelopes
    // serially, so a late tag can never be routed before its entry
    // exists: no window where the first tagged delivery falls back to
    // Incoming (F-004 review, Bug 2).              ← THIS COMMENT IS WRONG
    var data any
    if consumeOK.ConsumerTag != "" {
        perConsumer := &consumerEntry{
            deliveries: make(chan protocol.Deliver, 100),
        }
        ch.mu.Lock()
        ch.consumers[consumeOK.ConsumerTag] = perConsumer   // ← entry created here
        ch.mu.Unlock()
        data = perConsumer.deliveries
    }
    ch.resolve(env.RequestID, response{Data: data})
```

The SDK comment at lines 155-160 assumes that because readLoop is serial,
`basic.deliver` can never arrive before `basic.consume-ok`. This is **incorrect**.
Serial processing means envelopes are processed in arrival order, but the broker
sends the two envelopes from **different goroutines**, so arrival order is
non-deterministic.

### The race window

```
Time ─────────────────────────────────────────────────────────────►

Broker:
  registerConsumer(c)  →  dispatchLoop wakes  →  writes basic.deliver
  WriteEnvelope(consume-ok)

Network:
  [basic.deliver] [basic.consume-ok]          ← one possible ordering
  or
  [basic.consume-ok] [basic.deliver]          ← the other ordering

Client readLoop:
  receives basic.deliver   → ch.consumers[tag] == nil → Incoming (BUG)
  receives consume-ok      → creates entry → returns per-consumer chan (empty)
```

## Why it needs to change

1. **Pre-queued messages silently lost.** The F-004 acceptance criteria
   specifically requires this scenario to work. The bug violates criterion 5:
   *"a delivery routes to exactly one chan"*.

2. **Flaky in CI.** The race is timing-dependent; it manifests more often under
   `-race` but can occur in any environment. The commit message claims
   "previously-flaky pre-queued-delivery suites green -count=10" — that is
   incorrect.

3. **The incorrect SDK comment is misleading.** A future maintainer reading the
   comment at `channels.go:155-160` would conclude the race is impossible and
   not investigate. The comment must be corrected.

## How it needs to be countered

The entry must exist in `ch.consumers` **before** the first `basic.deliver`
for that tag can be routed. The client already knows the tag (client-
authoritative, minted by `nextConsumerTag`), so no broker round-trip is
needed.

### Option A — Pre-register in `Consume` (recommended)

Before sending `basic.consume`, create the entry under `ch.mu`:

```go
func (ch *ClientChannel) Consume(queuename string, ctx context.Context) (chan protocol.Deliver, error) {
    ...
    tag := ch.nextConsumerTag()

    // Pre-register: entry must exist before any basic.deliver can arrive.
    perConsumer := make(chan protocol.Deliver, 100)
    ch.mu.Lock()
    ch.consumers[tag] = &consumerEntry{deliveries: perConsumer}
    ch.mu.Unlock()

    if err := ch.client.writeChannelEnvelope(ch.id, protocol.BasicConsumeType, reqID, protocol.Consume{
        Queue:       queuename,
        ConsumerTag: tag,
    }); err != nil {
        ch.mu.Lock()
        delete(ch.consumers, tag)
        ch.mu.Unlock()
        return nil, err
    }

    select {
    case res := <-respCh:
        if res.Err != nil {
            ch.mu.Lock()
            delete(ch.consumers, tag)
            ch.mu.Unlock()
            return nil, res.Err
        }
        consumeOK := res.Data.(protocol.ConsumeOK)
        if consumeOK.ConsumerTag == "" {
            // Old broker: entry was created for nothing; clean up and
            // return the shared Incoming exactly as v0.2.0.
            ch.mu.Lock()
            delete(ch.consumers, tag)
            ch.mu.Unlock()
            return ch.Incoming, nil
        }
        // Entry already registered; return the pre-created chan.
        return perConsumer, nil
    case <-ctx.Done():
        ch.mu.Lock()
        delete(ch.consumers, tag)
        ch.mu.Unlock()
        ch.unRegisterREQ(reqID)
        return nil, ctx.Err()
    }
}
```

On the `BasicConsumeOKType` path in `route`: the entry already exists. The
`route` code can either skip the duplicate registration (idempotent: just
resolve with the existing entry's chan) or remove the registration entirely and
resolve with the entry it finds.

### Option B — Lazy registration in `route` (alternative)

In `route`, when a `basic.deliver` arrives with an unknown tag, create the
entry on the fly:

```go
case protocol.BasicDeliverType:
    ...
    if delivery.ConsumerTag != "" {
        ch.mu.Lock()
        target := ch.consumers[delivery.ConsumerTag]
        if target == nil {
            // Lazy: create entry for a tag that arrived before consume-ok.
            target = &consumerEntry{
                deliveries: make(chan protocol.Deliver, 100),
            }
            ch.consumers[delivery.ConsumerTag] = target
        }
        ch.mu.Unlock()
        target.deliveries <- delivery
        return nil
    }
    ch.Incoming <- delivery
    return nil
```

This is simpler but couples the routing path to consumer lifecycle, which is
less clean. It also means the consumer returned by `Consume` may have
deliveries buffered before it starts reading — acceptable but surprising.

### Option C — Guarantee consume-ok ordering in broker (not recommended)

The broker could guarantee that `consume-ok` is written before `dispatchLoop`
can write `basic.deliver`:

```go
func (q *Queue) registerConsumer(c *Consumer) {
    q.mu.Lock()
    q.consumers[c.tag] = c
    q.mu.Unlock()
    // Signal only AFTER the connection goroutine has written consume-ok.
    // This requires a synchronization primitive (e.g. a channel or WaitGroup)
    // between HandleConsume and dispatchLoop.
}
```

This couples the broker's dispatch timing to the client's protocol handshake
and adds latency for every consumer registration. It is correct but over-
engineered — the SDK should handle the protocol-level reality that delivers can
arrive before the OK.

### Recommended approach: Option A

- Cleanest: the entry lifecycle is managed in `Consume`, not in `route`.
- No dead entries: if consume-ok returns empty tag or error, the entry is
  cleaned up immediately.
- The `route` `BasicConsumeOKType` path simplifies: find existing entry,
  resolve with its chan (or fall through to `Incoming` if nil).
- Fixes the incorrect comment in `route`.

## Verification

After applying Option A:

1. `go test -race ./tests/ -count=10 -timeout 300s` — all green, zero flakes
   across the previously-flaky pre-queued-delivery suites.
2. The five F-004 regression tests pass individually.
3. `TestMultiProducer_NoConsumerThenAttach` specifically: 10/10 green under
   race (was 1-in-~30 failing).

## Scope

- **F-004 regression:** this bug is a sub-issue of the F-004 fix, not an
  independent finding. It is only reachable after the SDK v0.3.1 change.
- **Broker is correct.** No broker change is needed. The broker's dispatch
  timing is optimal and correct.
- **Tests unaffected.** The test code (`TestMultiProducer_NoConsumerThenAttach`)
  is correct — it correctly exercises the pre-queued-delivery scenario. The
  flake is entirely in the SDK's `route`/`Consume` lifecycle.
- **Single delivery guarantee is preserved.** Pre-registering the entry means
  deliveries always route to exactly one channel — never duplicated between
  `Incoming` and the per-consumer channel.
