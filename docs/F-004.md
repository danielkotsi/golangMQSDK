# F-004: Multiple consumers per channel cannot work end to end — the wire protocol discards the consumer's identity

Status: **OPEN** — missing feature; needs broker/protocol + SDK changes. Blocks
the F-001 "Option B" path from being usable by a real client.

## Finding

The F-001 broker-side fix (`RegisterConsumer` storing consumers by their actual
tag, `HandleConsume` echoing the resolved tag; see `reports/findings/F-001.md`)
made the broker *bookkeeping* support multiple consumers per channel, but the
feature is **not usable end to end**. A client cannot tell which delivery
belongs to which consumer, because the consumer's identity is thrown away at
the wire level and never reconstructed client-side:

1. `protocol.Deliver` (in this repo **and** in the SDK repo) has **no
   `consumer_tag` field** — `broker/protocol/events.go:92-97`. The broker's
   `dispatchLoop` picks a specific consumer (`consumer.tag`,
   `broker/queue.go:87`) and then writes an envelope that omits which consumer
   it selected (`broker/queue.go:101-111`).
2. The SDK's `Consume` returns the channel's **single shared `ch.Incoming`**
   (`channels.go:281`) regardless of which consumer was registered; it does not
   even read the `ConsumerTag` the broker returns — the `BasicConsumeOKType`
   branch of the SDK's `route` decodes `consumeOK` and immediately discards it
   (`channels.go:114-123`).
3. The SDK's `route` funnels **every** `basic.deliver` on the channel into that
   same `ch.Incoming` (`channels.go:104-112`), so deliveries from all queues a
   channel consumes are merged and indistinguishable.

Registering two consumers on one channel works broker-side, but both consumers
deliver into one merged stream: fan-in that was supposed to be made explicit
(F-001 Option B, point 3) is still implicit.

## Observed behaviour

There is no client-side work-around — the identity is gone before it reaches
the wire:

```
Consume("qa")  -> returns ch.Incoming (same chan for every consumer)
Consume("qb")  -> returns ch.Incoming (identical chan)

Publish to qa -> basic.deliver {body, exchange: "main", routing_key: "key"}
Publish to qb -> basic.deliver {body, exchange: "main", routing_key: "key"}
                  // no consumer_tag on either envelope;
                  // both land in the same ch.Incoming
```

A caller receives interleaved, unlabelled deliveries from both queues and can
only guess their origin by inspecting `Exchange`/`RoutingKey`. Nothing
distinguishes consumers, so per-consumer receive, cancel, or correlation is
impossible.

## Why that behaviour

- `protocol.Deliver` was defined before multi-consumer channels were on the
  table; it carries the message (tag, body, exchange, routing key) but not the
  recipient consumer tag.
- `dispatchLoop` selects a `Consumer` internally but stamps only channel-id +
  message fields onto the wire envelope — the connection-level routing key
  (`Consumer.channel.id`) is the only identifier present.
- The SDK mirrors the same wire struct (its `protocol/events.go:92-97` is
  byte-identical) and its `ClientChannel` holds exactly one receive sink
  (`Incoming`), created in `newClientChannel` (`channels.go:28-36`).
- `Consume` keeps the channel-level model: it registers a REQ, waits for the
  OK, and unconditionally returns `ch.Incoming` — the per-consumer
  `ConsumerTag` in the OK payload is parsed into nothing.

These three layers (wire struct, broker dispatch write, SDK consume+route) all
agree on the single-consumer model, so the feature is blocked at the protocol
boundary, not just at the SDK surface.

## Why it needs to change

1. **The F-001 Option B fix is incomplete.** F-001's own "How it needs to be
   countered" lists *"Make channel-level delivery fan-in explicit"* as a required
   step (`reports/findings/F-001.md`, Option B point 3). Without it, two
   legitimately-registered consumers on one channel still receive a merged
   stream — better than the silent overwrite of F-001, but still not "multiple
   consumers per channel".
2. **Cannot build on the feature.** A client that wants two consumers on one
   channel (e.g. the DLQ scenario from F-001) cannot filter reliably without
   the consumer tag; `Exchange`-based filtering is a fragile stand-in.
3. **No per-consumer cancellation/correlation.** Without a consumer identifier
   on deliveries there is no foundation for future `basic.cancel`, per-consumer
   prefetch, or per-consumer metrics.
4. **Cross-repo contract must be explicit.** The broker and SDK carry two
   identical-but-separate `protocol.Deliver` structs; adding the field requires
   a coordinated change and a documented version bump so the wire stays in sync.

## How it needs to be countered

The fix spans three layers in dependency order. Each step is independently
compilable and leaves the system working (degraded) for mixed-version mixtures.

### Step 1 — broker + broker protocol (`GolangRabbitMQBroker`)

- **`protocol/events.go`:** add `ConsumerTag string \`json:"consumer_tag,omitempty"\``
  to `Deliver` (`protocol/events.go:88-93`). Additive, `omitempty` keeps legacy
  envelopes well-formed.
- **`broker/queue.go`:** `dispatchLoop` stamps `ConsumerTag: consumer.tag` on the
  `Deliver` it writes (`broker/queue.go:101-111`; the consumer is already
  selected at `broker/queue.go:87`).
- Nothing else: `RegisterConsumer`/`HandleConsume` already store and echo the
  resolved tag. Acks/nacks already route per-consumer by delivery tag
  (`broker/channel.go:85-130`).

### Step 2 — SDK (`github.com/danielkotsi/golangMQSDK`)

- **`protocol/events.go` (SDK copy):** mirror the `Deliver` field addition.
- **`ClientChannel`:** add a `consumers map[string]chan protocol.Deliver`
  (tag → per-consumer chan), guarded by the existing `mu`, initialised in
  `newClientChannel`.
- **`Consume` (`channels.go:266-285`):** after the round-trip, read
  `consumeOK.ConsumerTag` from `res.Data.(protocol.ConsumeOK)`; if empty, fall
  back to `ch.Incoming`; otherwise allocate a fresh per-consumer chan
  (buffer 100, matching `Incoming`), register it under the tag, and return it.
  Signature stays `(chan protocol.Deliver, error)` — source-compatible.
- **`route` (`channels.go:104-112`):** forward each `basic.deliver` to
  `ch.consumers[delivery.ConsumerTag]`; fall back to `ch.Incoming` when the tag
  is absent (old broker / legacy delivery), preserving today's buffered,
  non-blocking send semantics.
- **Cleanup (`closeWithError`, `Close`):** close every per-consumer chan and
  `Incoming` exactly once (own once-close per chan), and clear `consumers`.
- **Client-authoritative tags (recommended):** have `Consume` send an explicit
  `consumer_tag` (e.g. `client.<ch>.consumer.<n>`) instead of relying on the
  broker echo; the broker already rejects duplicate tags
  (`broker/broker.go:88-89`).
- **Version bump:** SDK **v0.3.0** (wire-field addition ⇒ minor).

### Step 3 — wiring & tests (this repo)

- **`go.mod`:** bump `github.com/danielkotsi/golangMQSDK` v0.2.0 → v0.3.0 (after
  publish; no `replace`).
- **`tests/helpers.go`:** `collectDeliveries(Timeout)` and `assertNoDelivery`
  read `ch.Incoming` directly (`helpers.go:150-175,196-210`) — switch them to
  the per-consumer chan returned by `Consume`; add a `consumeOnChannel` helper.
- **New integration tests** (black-box, `startTestBroker`):
  - two `Consume` calls on one channel return **distinct** chans;
  - deliveries to Qa/Qb on one channel arrive **only** on their consumer's chan
    (fan-in explicit);
  - nack on consumer A's delivery redelivers **only** on consumer A's chan;
  - `Deliver.ConsumerTag` equals the tag from the matching `Consume`;
  - duplicate explicit tag surfaced as an error;
  - close closes all per-consumer chans.
- **F-001 regression guard** (`tests/finding_f001_test.go`) may be re-pointed at
  the per-consumer chan once this lands (its current Option-B path asserts via
  the shared `Incoming`).

### Compatibility matrix (during and after rollout)

| Broker | SDK | `basic.deliver` carries tag? | Behaviour |
|--------|-----|------------------------------|-----------|
| old | old (v0.2.0) | no | shared `Incoming`; single consumer per channel effectively enforced (F-001) |
| new | old | yes (ignored) | shared `Incoming`; multiple consumers registered but indistinguishable (current state) |
| old | new (v0.3.0) | no | tag `""` → not found → falls back to `Incoming`; behaviour unchanged |
| new | new | yes | **per-consumer chans; feature fully on** |

The feature activates only when **both** sides are new; the fallback guarantees
no regression for any intermediate mixture.

### Dependency order

1. Broker change (additive; old SDKs keep working).
2. SDK v0.3.0 (only after broker change).
3. `go.mod` bump + harness refactor + tests (only after SDK publish).

## Non-goals / deferred

- **Fixing F-002** (ack/nack data race) and **F-003** (missing
  `channel.close-ok`) — separate findings.
- **Delivery-tag ambiguity across queues on one channel.** Delivery tags are
  allocated per queue (`Queue.nextTag`), so two consumers on different queues of
  the same channel can hold the same tag number simultaneously; `HandleAck`/
  `HandleNack` match by delivery tag alone. Predates this feature (one consumer
  per channel made it unreachable) and only becomes reachable now. Follow-up
  options: include the consumer tag in `basic.ack`/`basic.nack`, or make
  delivery tags globally unique per channel.
- **Removing the unused broker-side `Consumer.ch`** — dead field, cleanup task.
- **Backpressure / slow-consumer policy, client-settable prefetch** — separate
  (perf/protocol) features.

## Acceptance criteria

1. `go build ./...` and `go vet ./...` pass with SDK v0.3.0 wired; no `replace`.
2. New same-channel multi-consumer tests pass repeatedly (`-count=3`), and the
   two chans from two `Consume` calls are provably distinct with no delivery
   leakage across them.
3. `TestFindingF001_SecondConsumeOnSameChannel` passes (per-consumer re-write or
   preserved fallback).
4. Existing delivery-reading suites pass after the harness refactor.
5. No data-loss window: a delivery routes to exactly one chan; legacy and
   per-consumer paths never double-deliver.
