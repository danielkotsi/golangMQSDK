## 1. F-004.1 — pre-queued deliveries silently fell back to `Incoming`

**Finding:** `docs/F-004.1.md`

### Root cause

The per-consumer entry was created in `route` when `basic.consume-ok`
arrived. The broker's `dispatchLoop` runs on a separate goroutine: it
wakes the moment a consumer is registered and can write `basic.deliver`
**before** the connection goroutine writes `basic.consume-ok`. When that
ordering hit the client, the tag had no registered entry, so the
delivery fell through to the legacy shared `ch.Incoming` — which the
`Consume` caller never reads. Pre-queued messages were silently lost
(observed ~1-in-30 under `-race`; `TestMultiProducer_NoConsumerThenAttach`
failed with `timed out after 5s waiting for 1 deliveries; got 0`).

The comment claiming that serial `readLoop` processing made the race
impossible was wrong: arrival order across two broker goroutines is
non-deterministic.

### Fix (Option A)

The client already owns the tag (`nextConsumerTag`), so the entry is now
pre-registered in `Consume`, under `ch.mu`, **before** `basic.consume`
is written:

- `Consume` allocates the per-consumer channel and registers it up
  front; every failure path (write error, broker error, unexpected
  payload, `ctx.Done`) deletes it before returning.
- `route`'s `BasicConsumeOKType` case no longer creates the entry — it
  looks the pre-registered entry up and resolves the pending `Consume`
  with its channel.
- Legacy broker (empty echoed tag): `route` resolves with `nil`,
  `Consume` deletes the pre-registered entry and returns `ch.Incoming`,
  preserving v0.2.0 behaviour.
- The incorrect race comment in `route` was replaced with an accurate
  one.

**Files:** `gomqSDK/channels.go`, `gomqSDK/multiconsumer_test.go`

**Tests:**
- new `TestF004_DeliveryBeforeConsumeOKRoutesToPerConsumerChannel` —
  reproduces the deliver-**before**-consume-ok ordering and asserts the
  delivery lands on the per-consumer channel, never `Incoming`;
- `TestF004_FirstDeliveryAfterConsumeOKNeverFallsBackToIncoming` updated
  to echo the actually-requested tag (as the real broker does) and runs
  100 back-to-back consume-ok + deliver iterations.

## 2. Send-on-closed-channel race on `Client.Close`

### Root cause

`route` (running on the `readLoop` goroutine) is the only goroutine that
sends on `ch.Incoming` and on per-consumer channels, and it sends
**outside** any lock:

```go
// channels.go — route, BasicDeliverType
if delivery.ConsumerTag != "" {
    ch.mu.Lock()
    target := ch.consumers[delivery.ConsumerTag]
    ch.mu.Unlock()                 // lock released
    if target != nil {
        target.deliveries <- delivery   // unsynchronized send
        return nil
    }
}
ch.Incoming <- delivery                 // unsynchronized send
```

`closeWithError` (invoked by `Client.Close` on a **user** goroutine)
clears the map and closes every channel:

```go
// channels.go — closeWithError
ch.consumers = make(map[string]*consumerEntry)
...
for _, e := range entries {
    e.closeOnce.Do(func() { close(e.deliveries) })
}
ch.closeOnce.Do(func() { close(ch.Incoming) })
```

A `Client.Close` racing between `route`'s lock release and its channel
send closed the destination channel first → **`send on closed channel`
panic**. Channel-level close via `handleChannelCloseOK` could not race
(it runs on readLoop, serial with `route`); only the user-goroutine
`Client.Close` path could.

### Fix (Option A)

`Client.Close` now stops the sender before closing anything:

1. `shutdown()` (unchanged),
2. snapshot and clear `c.channels`, detach `c.conn = nil` under lock,
3. close the socket to unblock the blocking socket read,
4. wait on a new `readLoopDone chan struct{}` (closed by `defer` in
   `readLoop`) — route has fully exited,
5. only then run `closeWithError` per channel,
6. `closeIncoming()` (unchanged).

Additionally, `route`'s delivery sends now `select` on
`<-ch.client.closed` so a full consumer buffer cannot pin readLoop
during shutdown (which would otherwise hang the new wait). Under normal
operation `c.closed` is never closed, so the select has exactly one
ready case and behaviour is unchanged.

**Files:** `gomqSDK/client.go`, `gomqSDK/channels.go`,
`gomqSDK/multiconsumer_test.go`

**Tests:**
- new `TestF004_CloseWhileRoutingDeliveriesDoesNotPanic` — floods
  per-consumer deliveries while calling `Client.Close` concurrently,
  asserts Close completes and the per-consumer channel is closed;
- existing close/drain/concurrency tests pass unchanged
  (`TestClientCloseIdempotentAndPendingDrain`,
  `TestClientConcurrentClose`, `TestClientChannelClose`,
  `TestOpenChannelExpiredContextReturnsDeadlineExceeded`).

## Behaviour impact

- **Normal operation:** unchanged. The delivery `select` has a single
  ready case; tags are opaque strings as before.
- **Shutdown:** `Client.Close` no longer panics; deliveries mid-shutdown
  are dropped rather than sent on a closing channel.
- **Pre-queued delivery:** guaranteed to route to the per-consumer
  channel, which was the F-004 acceptance criterion 5.
